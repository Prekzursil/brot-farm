Contribute

Three ways in, ordered by effort. Found a bug instead? The bug report form asks for the build hash and copy report text from the red error banner — that is all we need. Everything below is also written down in CONTRIBUTING.md.

1 · Submit a picture

No code. Find a variant in the playground, export it as an APRS record, drop it on the issue form — the intake bot validates and a human curates. Minutes.

2 · Add a fractal map

The build suite scaffolds, scouts, previews and checks a new map against the full quality bar: 100 % line+branch tests, docs card, catalogue parity. A focused evening.

3 · Platform changes

CI lanes and tool pins live in the quality-zero-platform repo — operator-only, PR + drift report required. Not for casual PRs.

Path 1 — submit an APRS record

APRS = Attractor Parameter Record Set — one experiment as a portable .aprs.json file (ADR 0001 · schema). Accepted records land in the community collection. Every screenshot below is a real capture of the exact step.

  1. Find a variant in the playground. Open the playground and scroll to the Experiments panel. 🎲 Surprise me composes a random valid grammar from the seed (same seed → same map), 🧬 Mutate this perturbs one operator of the current map, and the suggestion strip scores seeded candidates — click any thumbnail to apply it. Tune caps, window and tone gamma until the preview is worth keeping.
  2. Export it. Click 📦 export APRS. The browser downloads <name>.aprs.json — validated in-browser against the same field set as the Python validator before it is ever written.
  3. Validate locally — the same check the intake bot runs: 
    python scripts/validate_aprs.py s12345.aprs.json
    Prefer the terminal end-to-end? Author the same record from a build-suite map: python brot_build.py aprs my_map --out my_map.aprs.json.
  4. Open the APRS issue form at github.com/Prekzursil/fractal-darkroom/issues/new?template=aprs.yml. Drag & drop the .aprs.json file into the attachment field — the uploaded …aprs.json link in the issue body is what the bot downloads; pasted JSON without an attachment cannot be picked up. Add one line on why the map is worth keeping.
  5. The bot validates. The APRS intake workflow downloads your attachment, re-runs scripts/validate_aprs.py, rejects records without a preview hash, dedupes by preview hash against collection/, and comments pass/fail with reasons on your issue — usually within minutes.
  6. A human merges. On pass, the bot opens a curation PR adding collection/<preview-hash>.aprs.json plus the regenerated index. Nothing merges automatically — every entry is curated by hand. Curious what is already in? Browse the collection page; load any record back into the playground with load APRS… to see it render.

Path 2 — add a new fractal map

New maps enter through the build suite and must clear the full quality bar — check (below), CI's 100 % line+branch coverage, the docs card, and the Python↔JavaScript catalogue parity gate. The demo_* maps in usermaps/ are the reference examples.

# 1. scaffold a map from the operator grammar
#    real op f: cos sin tan sinh exp abs   imag op g: plain cos abs neg absxy
#    power 2..5 · families: mutation | fold | power
python brot_build.py new my_map --family mutation --real tan --imag plain

# 2. scout the sampling window (aim for an escape fraction in 0.15–0.9)
python brot_build.py scout my_map

# 3. fast deterministic preview + docs card thumb (docs/maps/my_map.jpg),
#    and regenerate the catalogue
python brot_build.py preview my_map

# 4. the full quality bar — must print: check: OK
python brot_build.py check my_map

# 5. full-quality render (user maps join the farm list automatically)
python brot_farm.py render my_map
  • Parity gate: every usermaps/*.py entry must appear in docs/assets/catalogue.js; regenerate it with python brot_build.py catalogue — never hand-edit it.
  • Tests: every new Python line is covered at 100 % line and branch by tests added in the same change (python -m pytest --cov; # pragma: no cover only on __main__ guards).
  • Before pushing: bash scripts/preflight.sh — all lanes, locally, before CI sees them.

Path 3 — quality-platform changes (operator-only)

The CI quality lanes are not defined here: .github/workflows/quality.yml calls a pinned reusable workflow from the quality-zero-platform (QZP) control plane, and even the biome version pin is read from QZP at runtime. Changes are operator-only and happen in the QZP repo, via PR with the Control Plane Verify and CodeQL checks required, and every profile/workflow PR must include a drift report — see QZP-DRIFT-REPORT.md for the exact command and format. If a platform change makes this repo red, the fix belongs in QZP — never weaken a gate locally to go green.

One rule above all

Every gate must pass for the right reason. The pull-request template is a 1:1 map of the CI gates — preflight lanes, 100 % line+branch coverage, the site suite, asset versioning, and the parity test — and reviewers re-run everything. Conduct: the Contributor Covenant 2.1 applies; security findings go to private vulnerability reporting, never a public issue.
